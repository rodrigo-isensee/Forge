# R-CONTRIB: Contribuição ao Forge - projeto abre PR, nunca mescla

Propósito: texto único desta regra; os outros arquivos citam o ID. Público: todo o time, em qualquer projeto. Revisão: 2026-10-14. Decisão: `docs/adr/0008-governanca-de-contribuicoes.md`.

- **Quem trabalha em um projeto abre PR para a `develop` do Forge e nunca o mescla**; mesclar no Forge é da sessão que mantém o Forge — `tech-lead` ou Jarvis numa sessão cuja raiz é um clone do próprio Forge — e do usuário na `main`. Uma sessão de projeto nunca é essa sessão, mesmo com o mesmo login.
- **Nenhum portão tem exceção, nem para o dono:** checks, pareceres e rótulos valem para todos os autores.
- **O rótulo `afrouxa-regra` é só do dono do Forge:** na sessão do Forge, o agente só o aplica (`gh pr edit|issue edit|pr create --add-label`, `gh api` em `issues/<n>/labels` ou `issues/<n>`, mutação GraphQL de rótulo) quando a conta autenticada no `gh` é a dona do repositório do Forge e há decisão do dono registrada; para qualquer outro contribuidor, aplicar ou delegar esse rótulo a um agente é **proibido**. O hook `conformidade` confere a conta (`gh api user`) contra o dono lido do `repository` do `plugin.json` e, na dúvida ou no erro de leitura, barra (falha fechado).
- **Checklist de merge** (Jarvis e `tech-lead`): na `develop` e na `homolog`, mescle apenas com: todos os checks verdes (`gh pr checks`), pareceres válidos (`forge-check pr`) e, se a catraca exigir, o rótulo do dono; na `main`, nunca (`R-MAIN`). O hook `conformidade` libera o merge ao `jarvis` e ao `tech-lead` só quando o hook `parecer` aceita; a `main` fica barrada para todos.
- **Sessão de outro projeto só propõe.** Ela pode: escrever a sugestão no corpo do PR (problema observado, proposta e como medir); criar **uma** branch própria `melhoria/<projeto>-<tema>` a partir da `develop`; abrir o PR para a `develop`. Ela **não pode**: commitar ou enviar em branch que não criou (a de outro PR, a `develop`, a `homolog`, a `main`); resolver conflitos nem revalidar pareceres de PR alheio; mesclar; fechar ou editar PR alheio; aplicar rótulos. **Issue nova no Forge é só da pessoa:** a sessão de projeto não cria issue (`gh issue create`, `gh api` POST em `issues` e a mutação GraphQL `createIssue` ficam barrados). A sugestão anônima é enviada pela pessoa, no terminal dela, fora do Claude, com `forge sugerir`; dentro do Claude o agente só a põe na fila, com `forge sugerir --guardar "<texto>"` (anonimiza e grava com permissão 600; nunca grava direto na fila). O envio mostra o texto final, avisa que aparece com o nome de usuário dela e só segue com a confirmação; nunca aplica rótulo. Aberto o PR, avisa o usuário e **para**: quem integra é a sessão do próprio Forge (`tech-lead` ou Jarvis), com a aprovação do dono. O hook `conformidade` barra, numa sessão cuja raiz não é o Forge, o `git push` (por remoto, URL, `-C`, `--git-dir`, `GIT_DIR`, `cd` ou `pushd`) para branch fora de `melhoria/<projeto>-`, `gh pr merge|edit|close|ready|reopen|review` e `gh issue create|edit|close|reopen` (o PR também é uma issue) com o Forge como alvo (`-R`, `GH_REPO` por `export`, `declare -x` ou `env`, URL ou número lido numa pasta do Forge: o clone de contribuição, qualquer clone do Forge, como o `~/Forge`, ou qualquer repositório com remoto que aponte para ele; o remoto nomeado do `git push` vale pela URL, lida com `git remote get-url`), `gh label` e `gh api` que editem, fechem, mesclem ou rotulem PR no Forge; as mutações GraphQL de rótulo, fechamento e edição de PR usam ID global e ficam barradas em toda sessão de projeto, inclusive por `--input` ou `@arquivo` (o que não dá para ler também). Os comandos de `bash -c`, `sh -c`, `eval` e `env -S` passam pelas mesmas regras, com as variáveis da linha externa; o que não dá para analisar e aponta para o Forge falha fechado. Quem é a sessão vem sempre da raiz dela (`CLAUDE_PROJECT_DIR`), nunca da pasta corrente, e o projeto vem antes do Forge: raiz com `.forge/versao` é projeto mesmo com o manifesto do Forge em `.claude-plugin/`, que no projeto só a sessão do Forge escreve. Um erro interno do hook diante de ação crítica também decide pela raiz: com a raiz num projeto, as regras dele e estas valem em qualquer pasta (o projeto, o clone, as worktrees, `~` ou outra) e no Bash, no Write e no Edit; com a raiz no Forge, valem as da sessão do Forge. Sem a variável, decide a pasta corrente, e em `~/.forge-contrib` a sessão é tratada como de projeto, de prefixo `melhoria/<nome do clone>-` (falha fechado). Pastas: a sessão de projeto usa só `~/.forge-contrib/<projeto>` e, se precisar, worktrees em `~/.forge-contrib/<projeto>-wt/*`; `~/.forge-contrib/wt/*` é exclusivo das sessões do Forge. Consequência: `gh pr edit --body` no próprio PR também fica barrado; ajuste o corpo por comentário (`gh pr comment`) ou peça ao dono. O hook lê o texto do Bash: um script ou uma ofuscação passa, e quem garante é o sandbox; o resto (commitar em branch alheia, resolver conflito) é só regra, pois o push dela já é barrado.
- O PR é indicado pelo nome da branch, não só pelo número.
- O clone de contribuição (`~/.forge-contrib/<projeto>`) nasce com `core.hooksPath` ativado.
