# R-CONTRIB: Contribuição ao Forge - projeto abre PR, nunca mescla

Propósito: texto único desta regra; os outros arquivos citam o ID. Público: todo o time, em qualquer projeto. Revisão: 2026-10-13. Decisão: `docs/adr/0008-governanca-de-contribuicoes.md`.

- **Quem trabalha em um projeto abre PR para a `develop` do Forge e nunca o mescla**; mesclar no Forge é da sessão que mantém o Forge — `tech-lead` ou Jarvis numa sessão cuja raiz é um clone do próprio Forge — e do usuário na `main`. Uma sessão de projeto nunca é essa sessão, mesmo com o mesmo login.
- **Nenhum portão tem exceção, nem para o dono:** checks, pareceres e rótulos valem para todos os autores.
- **Checklist de merge** (Jarvis e `tech-lead`): na `develop` e na `homolog`, mescle apenas com: todos os checks verdes (`gh pr checks`), pareceres válidos (`forge-check pr`) e, se a catraca exigir, o rótulo do dono; na `main`, nunca (`R-MAIN`). O hook `conformidade` libera o merge ao `jarvis` e ao `tech-lead` só quando o hook `parecer` aceita; a `main` fica barrada para todos.
- **Sessão de outro projeto só propõe.** Ela pode: escrever a sugestão no corpo do PR (problema observado, proposta e como medir); criar **uma** branch própria `melhoria/<projeto>-<tema>` a partir da `develop`; abrir o PR para a `develop`. Ela **não pode**: commitar ou enviar em branch que não criou (a de outro PR, a `develop`, a `homolog`, a `main`); resolver conflitos nem revalidar pareceres de PR alheio; mesclar; fechar ou editar PR alheio; aplicar rótulos. Aberto o PR, avisa o usuário e **para**: quem integra é a sessão do próprio Forge (`tech-lead` ou Jarvis), com a aprovação do dono. O hook `conformidade` barra, numa sessão cuja raiz não é o Forge, o `git push` (por remoto, URL, `-C`, `--git-dir`, `GIT_DIR`, `cd` ou `pushd`) para branch fora de `melhoria/<projeto>-`, `gh pr merge|edit|close|ready|reopen|review` e `gh issue edit|close|reopen` (o PR também é uma issue) com o Forge como alvo (`-R`, `GH_REPO` por `export`, `declare -x` ou `env`, URL ou número lido na pasta do clone), `gh label` e `gh api` que editem, fechem, mesclem ou rotulem PR no Forge; as mutações GraphQL de rótulo, fechamento e edição de PR usam ID global e ficam barradas em toda sessão de projeto, inclusive por `--input` ou `@arquivo` (o que não dá para ler também). Quem é a sessão vem sempre da raiz dela (`CLAUDE_PROJECT_DIR`), nunca da pasta corrente: com a raiz num projeto, as regras dele e estas valem em qualquer pasta (o projeto, o clone, as worktrees, `~` ou outra) e no Bash, no Write e no Edit; com a raiz no Forge, valem as da sessão do Forge. Sem a variável, decide a pasta corrente, e em `~/.forge-contrib` a sessão é tratada como de projeto, de prefixo `melhoria/<nome do clone>-` (falha fechado). Pastas: a sessão de projeto usa só `~/.forge-contrib/<projeto>` e, se precisar, worktrees em `~/.forge-contrib/<projeto>-wt/*`; `~/.forge-contrib/wt/*` é exclusivo das sessões do Forge. Consequência: `gh pr edit --body` no próprio PR também fica barrado; ajuste o corpo por comentário (`gh pr comment`) ou peça ao dono. O hook lê o texto do Bash: um script ou uma ofuscação passa, e quem garante é o sandbox; o resto (commitar em branch alheia, resolver conflito) é só regra, pois o push dela já é barrado.
- O PR é indicado pelo nome da branch, não só pelo número.
- O clone de contribuição (`~/.forge-contrib/<projeto>`) nasce com `core.hooksPath` ativado.
