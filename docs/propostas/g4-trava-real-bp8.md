# G4: trava real no lugar da lista de comandos proibidos (BP8)

Pedido v0478, etapa E99.1 (ordem do dono de 21/11 22:13, item 4). Só desenho: nenhum hook, código, teste, CI nem configuração do GitHub foi alterado. Tirar bloqueio de hook é decisão do dono (`R-CONFORMIDADE`, `R-DECISAO`). Público: o dono e o time. Revisão: 2026-12-21.

Ideia: a proteção passa a ser o que fica fora do alcance do agente (o sandbox do Bash, os rulesets do GitHub sem bypass, as tags protegidas e uma conta própria dos agentes com permissão mínima). O hook `conformidade` deixa de ser a fronteira e passa a orientar. A revisão de segurança para de procurar formas novas de escrever um comando. Dado do dono: os 8 itens de 21/11 com 6 a 26 voltas levaram de 4 a 66 h, quase todas nos hooks de comandos proibidos.

## (b) Bloqueios do hook: saem, viram aviso ou ficam

Critério: **fica** o bloqueio que protege o que nenhuma camada real cobre e que decide por dado estruturado (o `file_path` da ferramenta) ou por um alvo literal simples. **Vira aviso** o que uma camada real passa a cobrir depois dos passos do dono: o hook diz a forma certa e o vigia registra, sem barrar. **Sai** a maquinaria que só existe para fechar a lista negra contra grafias novas. A troca só vale para cada linha depois que o passo do dono que a cobre foi conferido (seção c, passo 12).

## (c) O que o dono faz antes, na ordem

Tudo na interface do GitHub ou no terminal do dono, fora do Claude. Nenhum agente faz estes passos nem recebe token para eles (`docs/protecao-de-branch.md`). A ordem importa: a conta dos agentes vem antes dos rulesets sem bypass, senão o próprio fluxo trava.

1. **Conta dos agentes.** Use uma conta de máquina (os termos do GitHub aceitam uma conta de máquina gratuita por pessoa, além da pessoal). Se a segunda colaboradora atual (papel `write`) é essa conta, use-a; senão, crie uma em github.com/signup, com 2FA ligado (Settings > Password and authentication).
2. **Acesso só `write` no Forge.** No Forge: Settings > Collaborators > Add people > a conta dos agentes > papel **Write** (nunca Maintain nem Admin). Aceite o convite na conta dos agentes. Confira: `gh api repos/<dono>/Forge/collaborators/<conta-dos-agentes>/permission --jq .role_name` → `write`.
3. **Token de escopo mínimo**, logado na conta dos agentes:
   a. Prefira o fine-grained: Settings > Developer settings > Personal access tokens > Fine-grained tokens > Generate new token. Resource owner: o dono do Forge, se a tela oferecer; Repository access: **Only select repositories** > Forge; Expiration: 90 dias. Permissões de repositório: Contents **Read and write**, Pull requests **Read and write**, Commit statuses **Read and write** (o G2 precisa), Actions **Read**, Checks **Read**, Issues **Read**, Metadata **Read**. **Nenhuma** outra: sem Administration, Workflows, Secrets, Variables, Environments, Webhooks, Deployments.
   b. Se o Forge não aparecer na lista do fine-grained (conta colaboradora num repositório de conta pessoal), use o clássico: Personal access tokens > Tokens (classic) > Generate new token (classic), Expiration 90 dias, marque **só `public_repo`**. Nada de `repo`, `workflow`, `admin:*`, `delete_repo`, `gist`, `user`, `write:packages`. O limite real fica no papel `write` do passo 2.
4. **Trocar o token dos agentes.** No terminal do dono, edite o `~/.claude/settings.json` (guarde cópia antes) e troque o valor de `env.GH_TOKEN` pelo token do passo 3. Para fechar a T12, tire o `GH_TOKEN` do `~/.claude/settings.json` e ponha-o só no `env` do `.claude/settings.local.json` da pasta do Forge (ignorado pelo git); cada projeto recebe a credencial dele no próprio `settings.local.json`. Reinicie as sessões. Confira na sessão do Forge: `gh api user --jq .login` → a conta dos agentes; e `gh api repos/<dono>/Forge --jq .permissions.admin` → `false`.
5. **Revogar o token antigo.** Na conta do dono: Settings > Developer settings > Personal access tokens > Tokens (classic) > apague o token que estava no `GH_TOKEN` (o de `repo`, `workflow`, `delete_repo`, `admin:org` e demais). Ele ficou legível a todo Bash dos agentes; revogar é a rotação. Se ele também servia a outro uso seu, crie outro, fora do alcance do Claude.
6. **Autoria dos commits (opcional).** Para o commit também sair da conta dos agentes, acrescente ao `env` do `.claude/settings.local.json` do Forge `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME` e `GIT_COMMITTER_EMAIL` com o nome e o e-mail `noreply` da conta dos agentes. Sem isso, o envio é do bot e o autor segue o do `~/.gitconfig` do dono (o que o README já descreve).
7. **Push protection.** Settings > Code security (ou "Advanced Security") > Secret Protection: **Enable**; Push protection: **Enable**. Gratuito em repositório público. Confira: `gh api repos/<dono>/Forge --jq .security_and_analysis.secret_scanning_push_protection.status` → `enabled`.
8. **Rulesets de branch, sem bypass.** Settings > Rules > Rulesets:
   a. Abra `checks-obrigatorios-develop-main`: em **Bypass list**, remova "Repository admin" (deixe vazia). Em Target branches, acrescente `homolog`. Marque **Restrict deletions**, **Block force pushes** e **Require a pull request before merging** (aprovações: 0; métodos permitidos: Squash e Merge). Confira em "Require status checks" que `bateria`, `bateria (python 3.14)` e `catraca` estão com a fonte **GitHub Actions**. Save. (É o `portoes` de `docs/protecao-de-branch.md` com outro nome; um só ruleset para não sobrar bypass esquecido.)
   b. Abra `merge-commit-homolog-main`: em **Bypass list**, remova "Repository admin" (vazia). Mantém o merge commit em `homolog` e `main`. Save.
   c. New branch ruleset `main-do-dono`: Enforcement **Active**, alvo só `main`, marque **Restrict updates**; Bypass list: só a conta do dono, modo **For pull requests only**. Create. Este é o único bypass, e só deixa o dono mesclar o PR na `main`; os checks dos outros rulesets continuam valendo para ele.
   d. `mainRuleset` (desligado, sem alvo): apague, para a conferência não confundir.
9. **Tags protegidas.** Rulesets > New ruleset > **New tag ruleset**: nome `tags-de-versao`, Enforcement **Active**, Target tags > Include by pattern `v*`. Marque **Restrict creations**, **Restrict updates**, **Restrict deletions** e **Block force pushes**. Bypass list: só o app **GitHub Actions** (o `release.yml` cria a tag com o token do workflow), modo Always. Create.
   b. Se a lista de bypass não oferecer o GitHub Actions, desmarque **Restrict creations** (fica a proteção de mover e apagar, sem bypass) e avise o time: a criação vira lacuna da T4 (cartão no `forge_sempre_atual`). Na próxima release, confira que o job `release` criou a tag.
10. **CODEOWNERS (com o time).** O time abre um PR com `.github/CODEOWNERS` dando ao dono os caminhos de controle: `.github/`, `.githooks/`, `.claude/`, `.claude-plugin/`, `.devcontainer/`, `hooks/`, `tests/catraca.py`, `tests/config.json`, `tests/neutralidade.py`, `tests/hooks/`, `docs/regras/`, `docs/adr/` e o próprio `.github/CODEOWNERS`. O `CODEOWNERS` não é workflow, então a conta dos agentes pode enviá-lo; o dono revisa e mescla o PR. **Só depois**, no ruleset do passo 8a, marque **Require review from Code Owners**. Confira com um PR de teste que toca `hooks/`: o merge fica bloqueado até a sua aprovação. Este passo é o substituto real do rótulo para arquivo de controle; pode ficar para uma segunda fase.
11. **Rede restrita do sandbox.** No `~/.claude/settings.json` do dono, ligue `sandbox.network.strictAllowlist: true` (comando no README, "Rede restrita de verdade"). Reinicie a sessão. Confira com `/sandbox`.
12. **Conferência (só leitura) e registro.** Para cada `<b>` em `develop`, `homolog`, `main`: `gh api repos/<dono>/Forge/rules/branches/<b>` deve trazer `pull_request`, `required_status_checks` (os três), `non_fast_forward` e `deletion`; para cada `ruleset_id` da resposta, `gh api repos/<dono>/Forge/rulesets/<id> --jq '{bypass_actors,enforcement}'` deve dar `bypass_actors: []` e `active`, salvo o `main-do-dono` (só o dono, `pull_request`). `gh api 'repos/<dono>/Forge/rulesets?targets=tag'` deve listar o `tags-de-versao`. Na sessão do Forge, `gh api repos/<dono>/Forge/rulesets/<id> --jq .current_user_can_bypass` deve dar `never`. Anote data e resultado no histórico do pedido e diga ao Jarvis quais passos estão feitos: só então os grupos da seção (b) que dependem deles podem virar aviso.

O que sai das permissões atuais, em resumo: o token clássico do dono no ambiente dos agentes (passos 4 e 5); o bypass "Repository admin, Always" dos dois rulesets ativos (passos 8a e 8b); o ruleset desligado `mainRuleset` (8d). O dono continua admin do repositório; perde só o atalho de mesclar sem checks, como já decidido em F8 (`docs/protecao-de-branch.md`).

## (d) O que muda para a revisão

- **Fim da caça.** A revisão de segurança não reprova mais por "outra grafia do mesmo comando passa pelo hook". Um grupo em aviso ou que saiu (seção b) não gera achado de contorno; a falta de orientação clara vira cartão para o dono do hook.
- **Critério de falha de segurança explorável no ambiente real** (o "salvo" do G1, item 1 da ordem). O achado bloqueia só com as quatro condições juntas: (1) ator realista: um agente na sessão normal, com o sandbox ligado e o token dos agentes; (2) a sonda roda no ambiente real (sandbox, token e rulesets em vigor), e não só no hook isolado: `rc 0` do hook não basta, é preciso o efeito; (3) o efeito é um destes: escrita em `develop`, `homolog`, `main` ou tag `v*`; merge sem os checks exigidos; mudança na configuração do repositório; leitura ou saída de segredo; escrita no estado em vigor não versionado (T9) ou nos caminhos de execução fora do sandbox (T11); chamada paga; (4) nenhuma camada da tabela (a) para o efeito. Fora disso é recomendação ou cartão, nunca volta.
- **Sonda no parecer.** Quem alega falha explorável registra em `## Sondas` a entrada literal e o efeito obtido no ambiente real (ex.: o `git ls-remote` mostrando a ref mudada, o arquivo alterado em `.forge/`). Sem efeito provado, não é bloqueante.
- **O que continua bloqueando sem sonda de efeito:** segredo no diff, mudança que enfraquece uma camada real (workflow, `.claude/settings.json`, `hooks/conformidade.json` nos caminhos que ficam, CODEOWNERS) e a lista branca do papel só de leitura recusando menos do que a ADR 0011 diz.
- **Mudança na própria camada real** (ruleset, token, sandbox) continua só do dono; a revisão confere pela leitura do passo 12, não pelo hook.

## (e) Riscos e como reverter

| Risco | Sinal | Reversão |
|---|---|---|
| Ruleset sem bypass trava o dono com a `develop` vermelha | botão de merge desabilitado | saída pelo conserto já documentada ("Develop vermelha sem bypass" em `docs/protecao-de-branch.md`); em emergência, o dono põe o bypass de volta no ruleset (um minuto na interface) e o tira depois |
| Ruleset de tag barra o `release.yml` | job `release` falha ao criar `vX.Y.Z` | passo 9b (tirar Restrict creations) ou acrescentar o GitHub Actions ao bypass |
| Token dos agentes vaza | alerta de secret scanning ou uso estranho no log de auditoria da conta | revogar na conta dos agentes (um clique) e gerar outro; o dano máximo é o de um colaborador `write` sem workflow: branches de trabalho e PRs, que não entram sem checks |
| Token expira (90 dias) | `gh` responde 401 | gerar outro com os mesmos escopos (passo 3) e trocar no passo 4 |
| Conta dos agentes perde algo de que o fluxo precisava (ex.: o G2 grava status) | 403 numa chamada do fluxo | acrescentar só aquela permissão ao token, com registro no pedido |
| Hook em aviso deixa passar e o efeito acontece onde a camada não chegou | vigia registra; incidente | voltar o grupo para bloqueio em `hooks/conformidade.json` (é dado, um PR) e abrir a dimensão que faltou na tabela (a) |
| CODEOWNERS deixa os PRs de controle esperando o dono | PR parado na aprovação | é o mesmo custo do rótulo de hoje; para desligar, desmarcar "Require review from Code Owners" |
| Volta completa ao estado anterior | — | reativar o bypass dos dois rulesets, apagar `main-do-dono` e `tags-de-versao`, repor o token antigo (novo, porque o antigo foi revogado) e reverter o PR que pôs os grupos em aviso |

## (f) Custo

Nada pago (`R-CUSTO`). O repositório é público e de conta pessoal: rulesets de branch e de tag, bypass list, CODEOWNERS com aprovação obrigatória, secret scanning e push protection são gratuitos nesse caso; os minutos do Actions também. Conta de máquina e token fine-grained ou clássico não custam.
Exige plano pago só se o Forge virar privado: no plano Free de conta pessoal, repositório privado não aplica rulesets nem proteção de branch, e a push protection privada é paga. Alternativa sem custo nesse caso: manter o repositório público, ou levá-lo a uma organização Free e reavaliar; sem nenhuma das duas, a camada do servidor não existe e os grupos da seção (b) não podem virar aviso (ficam como estão).
Opção sem custo e mais fina que o token, para depois: um GitHub App próprio instalado só no Forge (permissões por repositório e token de uma hora); pede um gerador de token na máquina, por isso não entra no primeiro passo.
