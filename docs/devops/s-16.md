## Detalhe dos achados
- R1 (recomendado) `tests/catraca.py:744` · Quando a API trava, cada chamada só desiste depois de 30 s (`tests/catraca.py:507`). O laço continua no próximo candidato quando a fonte devolve None (`:746`). No pior caso: 20 candidatos × até 7 chamadas (1 do PR, até 3 páginas de eventos, até 3 de execuções) × 30 s. Isso passa do `timeout-minutes: 10` do job. O resultado continua fechado: o job morre vermelho e nada passa. O custo é só esperar 10 min num runner gratuito. Sugestão para um pedido futuro: um prazo total para o terceiro caminho, ou parar no primeiro erro de API (hoje "a API falhou" e "o PR não se qualifica" dão o mesmo resultado).
- R2 (recomendado) `tests/catraca.py:739` · Limite de taxa do `GITHUB_TOKEN`: 1.000 requisições por hora por repositório. No pior caso, um run gasta cerca de 141 chamadas novas, além das que já existiam (eventos, execuções, PR). Cada `labeled`, `unlabeled`, `edited` ou `synchronize` no PR de promoção dispara um run, e o `concurrency` cancela o run antigo, mas as chamadas que ele já fez contam. No uso real (só promoção, só com violação de arquivo sem rótulo, saída cedo quando tudo fica coberto) o consumo fica bem abaixo do limite. Se o limite for atingido, a API responde 403, `_ou_none` (`:599`) devolve None e a catraca pede o rótulo, ou seja, fecha.

## Verificado
- **Tempo da catraca.** O terceiro caminho só roda quando sobrou violação sem rótulo e sem `R-CUSTO` (`:881-882`), e as violações precisam ser todas "mudança em <arquivo>". Fora disso, nada muda: nenhuma chamada nova. Num PR que não é de promoção, o custo é 1 chamada (`pr_atual`, `:739`). Numa promoção, o caso típico fica entre 3 e 7 chamadas por candidato, com teto de 20 candidatos (`:573`) e de 3 páginas de 100 por consulta (`:574`). Isso dá segundos. O trabalho de git por candidato (`ls-tree`, `merge-base`, diff) é local e barato, com `fetch-depth: 0` já presente.
- **Concorrência.** Não muda. O grupo continua `catraca-${{ github.ref }}` com `cancel-in-progress`, sem job novo nem matriz. Limite herdado, registrado na ADR 0008: o run da promoção não reroda sozinho quando o PR de origem é rotulado depois. É preciso um novo evento no PR da promoção.
- **Custo (`R-CUSTO`).** Zero. Repositório público, runner `ubuntu-24.04` gratuito, só o `GITHUB_TOKEN` (sem token pessoal, segredo ou serviço externo), sem cache nem artefato novo. O tempo extra fica dentro do mesmo job de 1 min.
- **Falha fechada.** A falha fechada vale em cinco pontos:
  - `api_com_teto` (`:579`) devolve None quando a resposta não é lista ou passa do teto de páginas.
  - `FonteGithub._ou_none` (`:599`) captura `OSError`, que inclui erro HTTP e tempo esgotado, além de `ValueError`, `KeyError` e `TypeError`.
  - `fonte_do_github` devolve None sem token, repositório ou número do PR.
  - O dono vem só do `tests/config.json` da base (`:869`) e, sem ele, nenhum rótulo vale (E4, só aperta).
  - A catraca que roda é a da base (`catraca.yml:41-45`), então o PR não troca o próprio juiz. A opção `--mesclados` só existe pela linha de comando, que o workflow da base não passa.
- **`forge-fechar`.** Nada muda. O script só fecha na `develop` (`bin/forge-fechar:7,38-40`), e o passo 5 só confere se o rótulo pedido está aplicado. O terceiro caminho só age em PR de promoção, que o `forge-fechar` não toca.
- **Trava da DV-5.** Nada muda. A trava de release fica no `forge-check sobreposicao --ref`, e a entrega não toca `bin/forge-check` nem os hooks.
- **Quando o ganho aparece.** Como a catraca roda a cópia da base, o caminho novo só passa a valer nos PRs abertos depois que a S-16 estiver na base de cada promoção. Hoje só a promoção `homolog` → `main` se beneficia (decisão do dono, alcance real "A").
