## Detalhe dos achados
Ambiente das sondas: fixture montada por `tests/test_hooks.py` (`Fixture.montar` e `rodar`), sessão de projeto (`CLAUDE_PROJECT_DIR={tmp}/proj`, `HOME={tmp}/home`, clone em `{tmp}/home/.forge-contrib/proj`), `agent_type: forge:tech-lead`, cwd no projeto. As mesmas sondas na base 3d8ad440 dão o mesmo código 0: os furos são anteriores, mas a entrega declara barrar envio e PR "falhando fechado" (R-LIMITES.md:56), e o portão é sobre esse requisito.

**A1.** Evidência: `hooks/conformidade.py:2631` decide o alvo só por `git remote get-url` lido no disco (`urls_dos_remotos`, :1275) ou pelo posicional como URL; `config_da_linha` (:2418) só olha `alias.` e refspec; `PUSH_COM_VALOR` (:145) pula o valor de `--repo` e `--repo=` nem é reconhecido; `git` (:2241) troca `pasta_git` a cada `-C` sem encadear; `subtree` não é lido como envio. Caminho de ataque: o agente da sessão de projeto, com a credencial do dono (que escreve no Forge), cria branch no remoto do Forge com uma das formas acima; é exatamente o que a diretriz 36 proíbe. Severidade: média (integridade do repositório da fábrica; a proteção da develop/main no servidor segue valendo). Correção mínima: (1) em `git_push`, tratar `--repo`/`--repo=<v>` como o remoto; (2) com qualquer `-c remote.*.url|pushurl` ou `-c url.*.insteadOf|pushInsteadOf` na linha, considerar o valor (aplicar `aponta_para_o_forge` ao valor da URL, e falhar fechado com `insteadOf` na linha); (3) encadear `-C` (`pasta_git = caminho(pasta_git, v)`), como o git faz; (4) `git subtree push|split --rejoin` com destino: o 1º posicional depois de `--prefix` passa por `git_push`. Esforço: P. Dono: autor da branch (dev do hook). Fixtures `dir36-*` novas para cada forma, com o lado `libera` (o mesmo comando apontando para o próprio projeto).

**A2.** Evidência: `hooks/conformidade.py:2871` extrai o slug só com `^/?repos/`; URL completa e `repositories/<id>` caem em `repo_env` (vazio) e depois em `alvo_do_forge(pasta, None)`, que olha o repositório da pasta (o projeto). Caminho de ataque: o agente abre PR (S7), fecha PR (S10), cria issue e aplica `afrouxa-regra` (S9) no Forge, burlando também a reserva do rótulo ao dono. O ID do repositório é público por leitura. Severidade: alta para S9 (contorna o rótulo que só o dono aplica, R-CONTRIB), média para o resto. Correção mínima: normalizar o endpoint antes do slug (tirar `https://<host>/` e `api/v3/`), aceitar `(^|/)repos/<dono>/<repo>`; com `repositories/<n>/` e método mutante em caminho de `CONTRIB_API`, falhar fechado na sessão de projeto (o ID não traz o nome, como já se faz no GraphQL em :2874). Esforço: P. Dono: autor da branch.

**A3.** Evidência: `git_no_forge` (:2636) cobre `commit`, `worktree add`, `branch <nome>` e `switch -c|checkout -b|--orphan`; passaram com código 0 no clone do Forge: `git merge origin/develop`, `git cherry-pick abc`, `git update-ref refs/heads/nova HEAD`, `git fetch origin develop:nova`, `git switch --track origin/nova`, `git checkout -t origin/nova`. Proporcionalidade: o efeito fica no clone local; sem envio (A1 corrigido) não chega ao Forge, então é recomendação. Correção sugerida: incluir `merge`, `cherry-pick`, `revert`, `am`, `rebase`, `pull`, `commit-tree`, `update-ref refs/heads/*`, `fetch` com destino e `--track|-t` em `BRANCH_NOVA`. Severidade: baixa. Esforço: P.

**A4.** Sobre o comentário em PR do Forge, pergunta do brief: deve virar achado, como recomendação e decisão do dono, não como bloqueio. O texto novo de `R-LIMITES.md:52` diz "não comenta", e o hook (`CONTRIB_PR`, :153; `CONTRIB_API`, :160) deixa `gh pr comment`, `gh issue comment` e `issues/<n>/comments` passarem, enquanto `gh pr review` (que também comenta) é barrado. Caminho de ataque realista: comentário com a conta do dono num PR do Forge é lido pelas sessões do Forge que revisam o PR (injeção de instrução por um canal que parece do dono). Impacto baixo, porque R-DECISAO não aceita decisão vinda de texto de PR. Recomendação: barrar os três (é a leitura literal da diretriz 36) ou tirar "não comenta" do texto; não deixar regra e hook divergentes. Dono da decisão: o usuário.

**A5.** `gh release create v9 -R <forge>`, `gh workflow run ci.yml -R <forge>` e `gh api repos/<forge>/dispatches` passam na sessão de projeto. A release cria tag `v*` no Forge (o canal de versão dos projetos; a ruleset de tags da E3.4 mitiga quando mesclada). Anterior a esta entrega; recomendo incluir `release` (create, edit, delete, upload) e `workflow run` no alvo do R-CONTRIB. Severidade: média para a release, baixa para o workflow. Esforço: P.
