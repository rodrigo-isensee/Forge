# Review de segurança: v0474 (MP6, E3.261)

Primeira rodada, head `7fc89fa3`, base `95a01e54`. Lido o diff inteiro de `bin/forge-copia`, `bin/forge-fechar`, `bin/forge-placar`, `bin/forge_disco.py` e os testes novos. Foco: a limpeza nunca apaga cópia com trabalho não enviado nem fora de `~/.forge-contrib/wt`; a recusa por disco falha fechada.

## Gatilhos
Gatilhos: controle do Forge (ferramenta de fechamento que apaga cópias), integridade de dados locais (rm -rf).

## Achados
- A1 (bloqueante) bin/forge-fechar:577 · clone que hospeda worktree ligada (git worktree add feito de dentro dele) é apagado sem olhar as worktrees dele: a mudança não commitada da ligada não conta, e a ligada fica sem repositório. Pendente se `worktree list` tiver mais de uma entrada.
- A2 (recomendado) bin/forge-fechar:578 · `rev-list --branches --not --remotes` ignora commit só em tag local (ou outra ref fora de refs/heads): o clone é apagado com ele. Trocar `--branches` por `--all` cobre tags, stash e notas numa leitura só.
- A3 (recomendado) bin/forge-fechar:577 · o `git status` roda o core.fsmonitor gravado no .git/config do clone, gravável de dentro do sandbox (~/.forge-contrib). Usar `git --no-optional-locks -c core.fsmonitor=` nas leituras do laço, como o forge-adotar (C-46-2).

## Detalhe dos achados
**A1.** Evidência: `bin/forge-fechar:569-586`; o teste de sujeira (`:577`) só lê a árvore do próprio clone. Caminho: não é ataque, é perda acidental pelo fluxo normal. Uma cópia em `wt/` que é clone (o caso desta mesma revisão) vira repositório-mãe de outra cópia quando alguém roda `forge-copia worktree` de dentro dela. Fechada a branch do clone, `rm -rf` leva o `.git` comum: a worktree ligada perde índice, HEAD e o vínculo, e o que estava só no índice se perde. Os commits das branches dela estão cobertos pelo `rev-list --branches` (refs comuns); a mudança não commitada, não. Isso fere o requisito do MP6 ("sem trabalho pendente"). Severidade: média (integridade local, sem atacante). Correção mínima: no laço, tratar como pendente o clone em que `git -C "$d" worktree list --porcelain` tiver mais de uma linha `worktree `, com a mesma leitura no lugar do comando que apaga, e um teste com a sonda S1. Esforço P. Dono: tech-lead (autor do E3.251).

**A2.** Evidência: `bin/forge-fechar:578`. Sondado: commit em HEAD solta com `git tag t-local` e volta à branch; o `--limpar` saiu com `clone=ok` e apagou o clone. Caminho: depende de alguém criar marca local sem enviar, o que o fluxo do Forge não faz (marcas v* só pela automação de release). Severidade: baixa. Correção: `git -C "$d" rev-list --all --not --remotes`. Esforço P. Dono: tech-lead.

**A3.** Evidência: `bin/forge-fechar:576-578` (todas as chamadas `git -C "$d"`). Sondado: `core.fsmonitor` no `.git/config` do clone; o `--limpar` o executou. Caminho: um agente que escreve em `~/.forge-contrib` (o `.git/config` dos clones é gravável no sandbox; o da cópia principal é protegido) grava o comando num clone da branch prestes a fechar. Quem roda o `forge-fechar --limpar` o executa, inclusive fora do sandbox se for o caso. A exposição já existe para qualquer leitura git feita numa cópia, e o ganho só existe se o fechamento roda com mais permissão que o agente: recomendação. `filter.*.clean` não se desliga por `-c` genérico; o fsmonitor é o caminho sem pré-condição de estado do índice. Esforço P. Dono: tech-lead.
