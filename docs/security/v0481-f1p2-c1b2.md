## Detalhe dos achados
**A4.** Evidência: `hooks/conformidade.py:303-305` (a tupla cobre `file`, `ext`, `git`, `ssh`, `http`, `https`); `docs/hooks.md:76` afirma "com todo transporte desligado na linha". Caminho de ataque: o agente, no sandbox, arma um repositório seu como na S5, com o host de destino que quiser (o sandbox do Bash nega hosts; o hook roda fora dele), e pede o Write de um parecer de item nesse repositório. O hook resolve o ref ausente, busca do promisor e o `git-remote-ftp` conecta. Ganho: canal de saída para host negado ao sandbox (o caminho e o usuário da URL levam dado) e o hook preso até o prazo do git (pela classe `ParecerDeItem`, a escrita estourou os 120 s do arnês, com o listener local fechando a conexão). Sem execução de comando (o `ftp` não usa `uploadpack`). Severidade média. Correção mínima, esforço P, uma das duas: (a) acrescentar à tupla `-c protocol.ftp.allow=never -c protocol.ftps.allow=never -c protocol.fd.allow=never`, cobrindo, com os seis de hoje, todo helper que o git 2.43 instala (`git-remote-ext`, `-fd`, `-ftp`, `-ftps`, `-http`, `-https`) e os embutidos (`file`, `git`, `ssh`); ou (b), mais robusto, `GIT_ALLOW_PROTOCOL=none` no ambiente desse git, que é lista de permissão e vence toda chave da cópia, inclusive a de helper com nome novo (sondado: `transport 'ftp' not allowed` com `protocol.ftp.allow=always` na cópia); exige que o `git` de `_comum` aceite esse ambiente. Corrigir também a frase de `docs/hooks.md:76`. Teste: o `test_uploadpack_da_copia_nao_roda_no_clone_parcial` (ou um irmão) com `remote.origin.url` `ftp://127.0.0.1:<porta>` de um listener local e `protocol.ftp.allow` e `protocol.ftps.allow=always`, esperando zero conexões. Dono: o autor do C1b-2.
